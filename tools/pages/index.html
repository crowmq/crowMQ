An intelligent messaging protocol for agentic systems

CrowMQ is a broker-centric publish–subscribe protocol in which the message queue becomes a first-class adaptive component. Messages carry the communication context an agentic workload actually depends on, and the broker is given a bounded set of decisions it may make about how that traffic is handled.

The bottleneck has moved from computation to communication

A 70-billion-parameter model needs roughly 280 GB just to hold its weights in FP32, or 140 GB in BF16 — already beyond a single 80 GB accelerator. At the trillion-parameter scale weight storage alone approaches 4 TB. Training is heavier still: FP32 training of Llama-2-70B with Adam is estimated at about 1.38 TB once gradients, optimiser states and activations are counted.

Work no longer fits on one device

Training and inference are forced across multiple accelerators, not as an optimisation but as a precondition for running at all.

So the devices must talk constantly

Participating devices continuously exchange gradients, parameters, activations, intermediate states and control information.

And that traffic becomes the limit

Part of the scalability problem shifts away from computation and memory and onto communication efficiency.

What the stack looks like today

Distributed AI systems rely on a layered set of communication mechanisms, each designed for a specific abstraction and pattern.

Accelerator and process level
NCCL and MPI provide collective operations — AllReduce, AllGather, ReduceScatter, All-to-All — for exchanging tensors between distributed workers.
Service level
gRPC carries remote procedure calls; MQTT and AMQP provide message delivery, flow control, reliability and delivery guarantees.
Agent level
MCP and A2A introduce interoperability for AI applications and agents, but their remote communication is still built on web-oriented mechanisms: JSON-RPC over streamable HTTP, HTTP+JSON/REST, or gRPC.
{{TICK}}

What that layering costs

Each layer is reasonable on its own. Stacked, they accumulate overhead that nobody owns.

  • synchronisation
  • serialisation
  • protocol framing
  • acknowledgement
  • connection management
  • intermediary processing
  • control traffic

The deeper problem is not overhead but separation. Communication decisions sit apart from AI workload semantics and from runtime infrastructure conditions, so a broker cannot jointly adapt message representation, priority, routing and delivery to workload urgency, resource availability, network conditions and communication cost.

Existing systems do offer QoS, message expiry, priority, acknowledgements and metadata. Those mechanisms are governed by predefined protocol or application policy, not by the runtime context of an agentic workflow.

What CrowMQ changes

The broker stops being a storage and forwarding mechanism governed by fixed rules, and becomes a bounded intelligent queue that adapts message handling to the communication context it can actually observe.

message context

Agent-aware semantics

Every message carries a compact envelope describing urgency, task class, dependency, validity, replacement relationships and delivery requirements — the communication properties of a message, never its application meaning.

runtime state

Observation of real conditions

Queue occupancy, message age, subscriber availability, acknowledgement behaviour and network state describe whether the system can currently satisfy what a message asks for.

bounded control

A finite set of decisions

Prioritisation, stale-message expiry, superseded-message replacement, duplicate suppression, adaptive buffering and congestion-aware delivery — and nothing beyond that.

CrowMQ does not replace agent reasoning or existing protocols. It provides an interoperable messaging layer that makes broker-mediated communication more timely, resource-aware, explainable and efficient, while application reasoning, agent goals and message content stay outside the broker's authority.

What the broker may do

These actions form the controllable part of the protocol. They are intentionally finite, because intelligence is applied where queueing delay, bandwidth consumption, redundancy and resource pressure actually arise.

  • Prioritise time-critical messages
  • Temporarily defer less urgent traffic
  • Batch compatible messages together
  • Remove messages whose validity has expired
  • Replace explicitly superseded updates
  • Suppress redundant transmissions
  • Adapt buffering and delivery behaviour

What it may not do

The boundary matters as much as the capability. Without it, communication intelligence turns into an unbounded autonomous agent sitting in the middle of the network.

  • Change an agent's objective
  • Modify the semantic content of a message
  • Assume the reasoning responsibilities of publishers or subscribers
  • Interpret prompts or reason about application goals

The Markov blanket gives this separation a formal shape: it defines exactly what the controller may observe and what it may influence, and everything else stays outside.

Three levels, kept apart on purpose

The separation between protocol semantics, message execution and adaptive control is central to the design. It lets communication intelligence influence how messages are handled without moving application-level reasoning into the messaging infrastructure.
