The protocol: context in the envelope, limits on the broker

CrowMQ follows the publish–subscribe model, so publishers and subscribers stay decoupled through topics and broker-mediated delivery. What it adds is a compact envelope describing the communication properties of each message, and a finite list of things the broker is permitted to do with that information.

This page describes the protocol as planned. The normative specification is deliverable D1, due at milestone MS1 in month four of the project. Field names and encodings here are indicative and will be replaced by the specification once it lands.

The message envelope

Each message contains its application payload together with the envelope below. These fields describe the communication properties of a message rather than its application meaning, which is what allows the broker to manage heterogeneous agent traffic without interpreting prompts or reasoning about goals.

FieldDescribesWhat it lets the broker do
identityA stable identifier for this message.Track progression, detect duplicates, correlate acknowledgements.
priorityRelative urgency within the topic.Order delivery when capacity is contended.
validityA deadline or validity period after which the message is no longer useful.Expire stale traffic instead of delivering work nobody is waiting for.
task classThe kind of traffic: task request, tool output, intermediate result, verification, memory update, coordination signal.Batch compatible messages and apply class-appropriate handling.
dependenciesThat another task is waiting on this delivery.Promote messages that are blocking downstream work.
supersessionThe message this one replaces.Drop an obsolete update once its replacement has entered the queue.
deliveryThe reliability and acknowledgement the sender requires.Choose retry behaviour without guessing.
provenanceWhere the message came from and what produced it.Attribute behaviour during analysis and keep adaptation traceable.
dependency

A verification result

It can declare that another task is waiting for its delivery, so the broker knows the message is on a critical path without being told what the verification means.

supersession

A revised state update

It can identify the message it supersedes. If the earlier one is still queued, sending both is wasted bandwidth and a chance for a subscriber to act on stale state.

validity

A coordination signal

It can expose its validity period. Once that period has passed, delivering it consumes capacity to produce an answer that is already wrong.

The action space

CrowMQ exposes a finite set of protocol-defined actions. A candidate action is applied only if it belongs to this space and satisfies the configured delivery, security and resource constraints.

ActionApplied whenEffect
prioritiseA deadline is at risk, or the message blocks a dependent task.The message moves ahead of lower-priority traffic in its queue.
deferCapacity is contended and this traffic can tolerate waiting.Delivery is postponed rather than dropped, freeing room for urgent work.
batchBandwidth is constrained and several messages are compatible.Aggregation reduces per-message overhead at the cost of some waiting time.
expireValidity has passed before delivery.The message is removed and the sender is informed.
replaceA message that explicitly supersedes a queued one has been admitted.The superseded message is removed before it can be delivered.
suppressA transmission is redundant.The duplicate is not sent, and the reason is recorded.
bufferA subscriber is unavailable but expected to recover shortly.Traffic is held rather than failed, within the configured memory budget.

Every one of these is a decision about communication management. None of them changes what a message says.

Delivery and acknowledgement

After validation and admission the broker maintains the state needed to track message progression and dependencies until delivery or expiry.

  • Subscribers are matched per topic, with one delivery per consumer group.
  • Acknowledgement behaviour is itself an observation: acknowledgement delay and retry behaviour feed the runtime state that drives adaptation.
  • A message that expires before delivery is removed and reported rather than retried.
  • Every significant adaptation retains the observations, the inferred condition, the selected action and the outcome.

That last point is what makes the behaviour examinable. Without a record linking system state to protocol behaviour, an adaptive broker is only a broker that sometimes behaves differently for reasons nobody can reconstruct.

The boundary

The protocol does not permit the broker to:

  • change an agent's objective;
  • modify the semantic content of a message;
  • assume the reasoning responsibilities of publishers and subscribers;
  • interpret prompts or reason about application goals.

When the controller lacks sufficient evidence, when uncertainty stays high, or when a decision cannot be completed inside its processing budget, CrowMQ continues with a valid deterministic policy. An uncertain decision never gets to affect message delivery.

Where it sits alongside what you already run

CrowMQ complements existing messaging and agent-interoperability standards rather than competing with them. It addresses how messages should be managed when their urgency, dependency, validity and communication value change at runtime.

LayerExamplesHandlesRelationship to CrowMQ
Collective communicationNCCL, MPITensor exchange between distributed workersStays underneath; CrowMQ does not replace collectives.
Remote procedure callgRPCRequest and response between servicesComplementary transport for point-to-point calls.
Message deliveryMQTT, AMQPDelivery, flow control, reliability, QoSClosest relatives. CrowMQ adds runtime-adaptive handling on top of similar primitives.
Agent interoperabilityMCP, A2AHow agents and tools describe and call each otherCrowMQ carries this traffic; it does not define agent semantics.
