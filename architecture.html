A light message path with a control loop beside it

The architecture combines a lightweight data plane with a bounded adaptive control loop. Routine publication, queue access, subscriber matching and delivery execute according to the currently active policy, without running a full inference procedure for every individual message.

figure 2 · the CrowMQ broker

Publishers attach an envelope and publish through the input interface. The data plane admits, queues and delivers. The control plane observes what is happening, infers the state of the communication process, and issues control signals that change how the queues behave.

The data plane

The high-frequency path. Everything here runs per message, so it has to stay cheap.

01

Admission and validation

The envelope is checked against protocol rules and topic configuration before the message is allowed into a queue.

02

Adaptive message queues

One per topic. The broker holds the state required to track message progression and dependencies until delivery or expiry, rather than applying one fixed handling rule to all traffic.

03

Delivery engine

Matches messages to subscribers and enforces the active policy on ordering, batching and deferral.

04

Acknowledgement and retry

Settles deliveries, schedules redelivery where the envelope requires it, and reports outcomes back into the observation layer.

The control plane

Three components, each with a narrow job.

Runtime observation layer
Characterises the current communication environment from queue state, arrivals, deliveries, resource usage and subscriber state.
Active Inference controller
Maintains beliefs about conditions that cannot be measured directly, evaluates the permitted actions, and selects a policy.
Policy manager
Enforces protocol constraints, holds the safety fallback, and governs how quickly adaptation is allowed to happen.
Inside the controller

What the observation layer watches

Message metadata expresses what a message requires. Runtime telemetry describes whether the system can currently satisfy it. The two are only useful together.

  • queue occupancy
  • message age
  • waiting time
  • arrival rate
  • service rate
  • payload size
  • acknowledgement delay
  • retry behaviour
  • subscriber availability
  • delivery success
  • network capacity
  • broker CPU
  • memory utilisation

Observed jointly, these expose situations a static queue configuration cannot represent: persistent queue growth, impending deadline violations, subscriber unavailability, changing resource pressure, and congestion that is either temporary or sustained.

Why the two paths are separated

A decision mechanism that costs more than the communication it improves is not an improvement. The separation between the message path and the control path is what keeps the adaptation affordable.

Per-message work stays small

Publication, queue access, matching and delivery follow the active policy. No inference runs on the critical path of an individual message.

Control runs on its own clock

The controller aggregates observations over configurable windows, updates its beliefs, and reconsiders the active policy when the observed state has changed enough to justify it.

Different situations, different timescales

Stable traffic continues with minimal control activity. Rapid queue growth, changing subscriber availability, resource pressure or repeated service-level violations trigger earlier reconsideration.

The cost of inference is itself monitored as part of the resource state, so communication adaptation stays beneficial instead of becoming a new broker bottleneck.

Persistent storage

Four things are kept, and each has a consumer.

Queue and metadata
Message state, dependencies, supersession and expiry — what the data plane needs to resume correctly.
Runtime statistics
Telemetry and history, which give the controller something to infer from rather than a single instantaneous reading.
Adaptation logs
Decisions, the observations behind them, and the outcomes that followed.
Configuration
Preferences, constraints and protocol rules, including the operating region an application wants to favour.

Safety and traceability

Runtime adaptation stays subject to explicit protocol constraints and conservative operating rules.

  • An action is applied only if it belongs to the permitted action space and satisfies the configured delivery, security and resource constraints.
  • Insufficient evidence, high uncertainty or an exhausted processing budget all fall back to a valid deterministic policy.
  • Each significant adaptation records the observations, the inferred communication condition, the selected action and the observed outcome.

That record provides a traceable relationship between system state and protocol behaviour, and lets the effectiveness of individual decisions be examined experimentally rather than argued about.

The prototype

A reference implementation will instantiate the specification and provide the experimental platform: protocol implementation, publisher and subscriber libraries, reference broker, adaptive message queues, runtime telemetry and the Active-Inference control mechanism, integrated into one system.
